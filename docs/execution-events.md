# Execution events

Use `python tsim.py run examples/vector_add.cu --events` to save `execution-events.jsonl` and `execution-summary.json` in the run directory. `--events-limit` bounds the entire record stream (default 200,000); one terminal truncation marker is additional. This stream describes actual CPU PTX execution. It contains no hardware-cycle predictions. The existing `--trace` inspector stream remains independent and both can be enabled together.

A stream header records schema and coverage. Launch records identify grid/block dimensions, static/dynamic shared storage, and a PTX liveness estimate for registers, explicitly distinguished from NVIDIA ptxas allocation. Issue records identify launch, block, warp, function, monotonically allocated call-frame generation, PC and generated PTX line. Virtual register keys are `id * 2 + wide`; narrow and wide register files have distinct keys. Ordinary uses and definitions apply to `execution_mask`; `predicate_use` applies to `path_mask`. Virtual register counts are interpreter declarations, not physical occupancy measurements. Call ABI slots, implicit carry state, and complete scoreboard dependencies remain unmodeled.

Memory records carry their parent issue, lane, element, operation, width, resolved space and hexadecimal 64-bit virtual address. Only successfully completed accesses are recorded. Each supported issue records its expected access count and width; the reader checks conservation at completion and rejects missing or duplicate lane/element records. Faults may retain a completed prefix. Scalar/vector `ld` and `st`, including kernel parameter reads, and scalar `atom`/`red` are captured. An atomic produces one logical RMW record rather than separate read/write records. Local addresses name private lane storage: identical offsets in different lanes are not broadcasts. Generic addresses are resolved into shared, local, parameter or global space using the interpreter's routing windows. Explicit `ld.const` preserves its constant-bank classification even though the functional storage comes from a module global allocation.

Each CPU worker keeps its current issue parent in thread-local storage. A mutex serializes output and assigns sequence numbers; four workers can interleave instructions without attributing an access to another worker. Capture explicitly selects reference execution, preserving numerical results while avoiding memory paths that bypass observation. Single-worker seeded runs replay identically; multiple-worker ordering is not guaranteed to replay identically.

Instruction, launch and stream completion records establish boundaries. A fault preserves preceding successful lane accesses and marks the instruction/launch as faulted. File-open and write errors are reported. Missing completion, truncation, process failure, timeout or a coverage gap prevents a complete-memory claim. Async copies, tensor/texture/surface paths, vector/128-bit atomics, device calls and other uncaptured paths emit coverage gaps; these are executable functional features, not complete timing inputs. `complete_scoreboard_dependencies` is always false at this stage.

The summary counts observed logical accesses and requested bytes separately by memory space and operation. It does not equate an interpreter issue with a SASS instruction, requested bytes with DRAM bytes, or parameter slots with physical memory transactions. Dispatcher counters for ordinary loads/stores now use resolved spaces after successful execution; generic shared/local requests no longer inflate global traffic. Explicit constant-bank reads are excluded from those global counters. Existing local-sector and shared-bank counter formulas are inherited address proxies; the new event stream preserves the information needed to replace them with separately specified transaction models.

`python tsim.py event-conformance` verifies exact vector and 3D traffic, mixed generic spaces, scalar atomics, constant/local identity, call frames, PTX alignment, four-worker parent identity, seeded replay, capture equivalence, malformed input rejection, fault prefixes, event caps and disk errors. It also verifies pristine/older patch-stack replay and protection of unknown local edits. Recorded evidence is in [event-conformance.json](event-conformance.json).

Patch replay uses an isolated scratch Git repository, including when the cache is inside the main checkout. Git can otherwise silently skip patch paths while returning success from a subdirectory. Setup rejects a replay that changes no target files, and the regression fixture exercises the nested cache layout.
