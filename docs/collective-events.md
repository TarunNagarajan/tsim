# Executed collective groups and source lanes

`python tsim.py run SOURCE.cu --events` now records actual shuffle, vote, warp reduction and matching dispatches. The header declares additive `collective_schema: 1` with typed dependency schema 2. `execution-summary.json` reports dispatch groups, destination maps, contributing source-lane reads, wait attempts and undefined shuffle sources. These are observed interpreter operations, with no GPU-cycle prediction.

An ordinary issue record describes the selected path after predication. A collective can first wait for named lanes on another path, or dispatch separately for several runtime membership groups. The new records come from the executed handlers after the interpreter resolves that behavior; a mnemonic or membership-mask spelling cannot establish the actual source lanes.

`collective_wait` identifies an attempt that parks before dispatch. It has no result write or transfer map. `collective_group` identifies an actual dispatch, its parent issue, operation kind, executing lane mask, virtual data-source key and data-dependent destination keys. Its sequence number identifies the group. `collective_transfer` links that group to one destination lane and the mask of contributing source lanes. Group and issue ownership remain explicit when independent blocks execute on different CPU workers.

For shuffles, the map records the actual selected source after index, segment and clamp handling. An out-of-range selection that falls back to the destination's own value therefore records its own lane. An inactive source records a zero source mask and increments `undefined_shuffle_sources`; the interpreter's zero result does not establish defined NVIDIA behavior or a register producer. The optional shuffle predicate depends on selection controls rather than transferred data, so it is excluded from `data_defs`.

Votes, warp reductions and matching read the data contributed by every lane in their actual dispatch group. Each result map records that group mask. The source key retains narrow/wide virtual-file identity, including wide matching operands and predicate vote inputs. A nonvirtual data operand has key `-1` and creates no fabricated virtual-register transfer. The record covers virtual data-source dependencies; it does not encode every special-register state dependency.

The reader checks group kind, parent ownership, typed source/destination roles, nonempty and disjoint executing masks, valid destination lanes, unique maps and source containment. A shuffle reads at most one source lane; a vote/reduction/match requires every contributing group lane. Successful completion requires exactly one map per destination lane when a virtual source and data destination exist, and full dispatch participation unless the attempt waited or was fully predicated off. Faults retain completed prefixes; caps and incomplete streams prevent completeness. `complete_supported_collectives` requires a declared contract and successful complete capture; it describes the four supported families, while the complete GPU scoreboard remains unimplemented.

The [dependency conformance report](dependency-conformance.json) passes 219 checks, including 43 independent collective-contract references. Real CUDA shuffle maps match twenty width/mode references per warp, including widths 2 through 32 and own-lane fallbacks. Runtime masks produce disjoint groups of 16 lanes for votes, reductions and matching, with source maps invariant across two profiles and three schedules. A four-block reference delays lane zero, captures actual parked attempts and reconverged lane-zero transfers, and checks all 384 numerical outputs with four CPU workers. Deleted maps, changed ownership, invalid source masks and missing participation are rejected.

The current [register hazard graph](register-dependencies.md) still refuses these collective instructions. Consuming the maps must preserve source-to-destination lane identities, read all input versions before replacing in-place destinations, and distinguish selection reads from actual result writes and waits. Election, block reductions, tensor collectives, call ABI transfers, control/synchronization readiness and physical pipelines require further modeling. Capturing a legal CPU execution does not establish every physical-GPU reconvergence or weak-memory outcome.
