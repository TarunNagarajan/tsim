# SM resource ceilings and admission

`python tsim.py residency-report RUN_DIRECTORY` writes `sm-residency.json`. It combines captured block shape, shared memory and the explicitly labeled PTX register estimate with public A100/H100 capacities. This is a theoretical resource ceiling under the specified inputs, not measured achieved occupancy or an assertion that NVIDIA's compiler allocates the same registers.

The public limits include 64 warps, 32 resident blocks, 64K 32-bit register slots and at most 1024 threads per block. A100 has 164 KiB shared memory per SM and 163 KiB user shared memory per block; H100 has 228 KiB and 227 KiB respectively. Block dimensions, warp size and other capacities follow the [CUDA 12.6.3 technical specifications](https://docs.nvidia.com/cuda/archive/12.6.3/cuda-c-programming-guide/index.html#technical-specifications-per-compute-capability), [Ampere tuning guide](https://docs.nvidia.com/cuda/archive/12.6.3/ampere-tuning-guide/index.html#occupancy) and [Hopper tuning guide](https://docs.nvidia.com/cuda/archive/12.6.3/hopper-tuning-guide/index.html#occupancy).

The model accounts for partial warps, register allocation in 256-slot warp units, four register partitions, 128-byte shared allocation units, a 1-KiB system reservation per block and the separate register admission check that rounds block warps to partition count. These rules are verified against the installed CUDA 12.6.3 standalone `cuda_occupancy.h` calculator. That SDK accepts 256 allocated slots per thread on SM8/9; this allocation count differs from the ISA's 255 logical-register limit. Larger PTX estimates require a physical allocation/spill result and are rejected without inventing spills. Maximum shared carveout and permitted dynamic shared opt-in are explicit input assumptions. The default PTX report assumes one ordinary block barrier. With compiler evidence it uses the actual ptxas count. The pinned SDK applies a 64-barrier SM ceiling on Hopper; it does not apply that ceiling to Ampere, so this SDK model does not establish Ampere barrier capacity. Driver attributes, launch bounds, clusters and dynamic register redistribution remain outside this model.

Reports include every resource ceiling and all tied limiting resources. Warp occupancy and useful active-thread fraction remain separate for partial warps. Combined static/dynamic shared memory is rejected in PTX-only reports because captures omit the aligned dynamic storage prefix; summing static and dynamic byte counts could undercharge a block. `--compiler-resources DIRECTORY` accepts verified NVIDIA compiler allocations instead, retaining both the PTX estimate and compiler data. The [compiler contract](compiler-resources.md) describes exact shared-prefix handling and the separation between compiled allocations and PTX event replay.

`SMResidency` implements atomic admission and release. It tracks live block identities, warp slots, shared storage, barriers and per-partition register charges, with a declared rotating balanced warp-placement policy. Failed admissions leave every resource unchanged; releasing a block returns exactly its charges. Placement and fragmentation are synthetic choices, and this allocator is not yet wired to the functional interpreter or cache replay. No issue scheduler, scoreboard, memory queue or GPU cycle model is claimed.

`python tsim.py residency-conformance` checks boundary cases and 300 mixed admission/release steps, then compares 3872 allocation/resource cases and homogeneous allocator fills with NVIDIA's standalone SDK calculator, including barrier counts of zero, one, four and sixteen. It also runs fresh numerical CUDA checks for A100/H100 vector addition, dynamic shared reduction, three private-memory launches and the rejected PTX-only aligned prefix. The [recorded report](residency-conformance.json) includes the SDK header hash and model hash. SDK differential verification runs entirely on the CPU and does not establish physical-GPU differential accuracy.
