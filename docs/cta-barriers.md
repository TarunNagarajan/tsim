# CTA barrier phases

All sixteen CTA barrier resources now use independent phase state. Each phase records its participant warps, waiters, thread-count mode and reduction operation. Completion restarts only that phase's waiters and resets its state for immediate reuse. Reduction results are copied to each waiter before reuse, so a fast warp cannot overwrite the answer a slower warp has yet to collect.

`bar.sync` without a count and the corresponding whole-CTA reductions wait for every non-exited warp at the same barrier ID. Waiting at another barrier is insufficient. Exits can complete an all-CTA phase, and the scheduler checks this before selecting its next warp. A partial warp contributes its actual live predicate votes. Explicit counts remain nonzero multiples of the configured warp size, and arrivals are counted in whole warps. `bar.arrive` contributes without parking; synchronization and reduction waiters park until their own phase completes.

A blocking arrival ends its warp's scheduling turn even when that arrival completes the phase immediately. This allows earlier waiters to run before the final arrival enters a polling loop. A bounded deterministic regression verifies this for both whole-CTA and counted barriers. Nonblocking `bar.arrive` retains its continuation behavior.

The implementation diagnoses crossed barrier deadlocks, duplicate warp arrivals before phase completion, nonuniform IDs or counts within an arriving warp, inconsistent counts between warps and mixed reduction operations. Mixing whole-CTA and explicit-count forms in one active phase is currently refused, including a numerically equivalent full-block count. Mixing sync/arrive with reduction is also refused. The supported execution model requires convergence of a warp's live lanes; arbitrary independent-thread rendezvous is not implemented.

Shared-memory happens-before tracking snapshots each producer's clock at arrival and grants the joined clocks only to waiters on completion. A producer's later writes do not become ordered merely because its earlier `bar.arrive` completes. An exit does not fabricate an arrival or a publication snapshot for that warp.

The previous implementation released all uncounted waiters whenever the runnable list was empty and accumulated whole-CTA reductions in one block-wide object. Consequently, warps waiting on different IDs could restart together, and an uncounted barrier could borrow a warp parked at an unrelated counted barrier. The added regressions linked against the previous static engine library passed 7 of 19 tests; twelve failed, including the new phase diagnostic. The repaired tests are shipped in the replayable engine patch and run through `python tsim.py conformance` in CI.

Changing the valid scheduling order exposed an older async-copy test that arrived twice per consumer. A consumer warp could satisfy its initialized arrival count before the producer issued `cp.async`. The repaired reference uses one arrival per consumer and waits on the initialized phase's parity; the producer's `cp.async.mbarrier.arrive.noinc` provides the remaining arrival after its copy completes. The exact corrected PTX is accepted by the pinned NVIDIA assembler. This verifies syntax and compiler acceptance, not execution on a physical GPU.

The CUDA source fixture `tests/conformance/cta_barrier_phases.cu` supplies separate host arithmetic references. Each run checks 49,330 values across 19 launches, ten block sizes, seven reduction rounds, early exits leaving 17 live lanes and repeated handoffs between two independent counted pairs. `source-conformance` runs it on A100/H100 profiles with deterministic, adversarial and seeded random schedules and four CTA workers, alongside the publication and post-arrival race references. These are functional CPU tests, not physical-GPU differential evidence.

The semantics follow the [CUDA 12.6.3 PTX barrier specification](https://docs.nvidia.com/cuda/archive/12.6.3/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-bar-barrier) and its [exit rules](https://docs.nvidia.com/cuda/archive/12.6.3/parallel-thread-execution/index.html#control-flow-instructions-exit). The architecture event stream does not yet expose typed CTA arrival/release records, and timed SM replay continues to refuse block barriers. Capturing those transitions and gating memory completion before release are the next integration steps; functional completion alone does not establish a timing model.
