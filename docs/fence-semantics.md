# Typed PTX fences

The interpreter preserves the meaning and operands of `fence` and `membar` instructions instead of converting every spelling to an empty, sequentially consistent host fence. The replayable `zzz-fence-semantics.patch` follows the existing five engine patches; their contents and the pinned engine revision remain unchanged.

The AST distinguishes ordinary thread fences, old-style membar, alias and async proxy fences, directional tensor-map proxy fences, and operation-restricted mbarrier initialization fences. It retains ordering semantics, synchronization scope, proxy state-space filters and the tensor-map acquire address/range. Pre-Volta membar has a separate legacy category. These categories follow [NVIDIA PTX ISA 8.5](https://docs.nvidia.com/cuda/archive/12.6.3/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-membar).

Parsing validates modifier combinations, operands, PTX versions and SM targets. Exact fence modifiers bypass the general parser's cache-hint stripping and `::cta` normalization. A tensor-map acquire requires an immediate range size of 128; its address contributes to register liveness and dependencies. Ordinary fences require an explicit scope. NVIDIA's pinned CUDA 12.6.85 assembler rejects `fence.sc` without a scope, despite a scope-free example in the manual; the syntax rule and assembler agree.

During eager functional execution, ordinary SC fences and legacy membar use a sequentially consistent host fence, acq_rel and bidirectional proxies use a host acquire/release fence, and directional/restricted forms use their acquire or release host fence. CPU fences are unscoped and can provide stronger ordering than PTX requires. They do not implement the PTX scoped synchronization axioms, proxy completion, cache invalidation or a detailed GPU fence latency. A fence never becomes a CTA barrier. The interpreter evaluates active tensor-map acquire address registers, diagnoses uninitialized registers, rejects its private shared/local/parameter address windows and overflowing range ends, and leaves the memory bytes untouched. It does not dereference the range or prove that the entire range is a live allocation. A false predicate skips operand evaluation.

The [recorded proof](fence-semantics-conformance.json) checks 112 independently specified syntax/metadata cases: 52 accepted and 60 rejected. Of these, 110 agree with the NVIDIA assembler; two old sm_10/sm_20 membar cases are parser-only because CUDA 12.6 no longer assembles those targets. Both GCC and Clang harnesses check address operands, file widths, offsets, predicates and register dependency roles. Each also performs 2,119 eager execution checks: divergent single-lane fences under three schedulers, unchanged tensor-map ranges, bad operand diagnostics and false-predicate suppression. Generated cubins establish assembler acceptance, not execution on a physical GPU.

Run `python3 tests/fence_semantics_components.py --cache .local --out .local/fence-semantics-conformance` after setup in Ubuntu. The proof records normalized source/patch hashes, compiler identities, assembler identity, per-case inputs/diagnostics and generated cubin hashes. CI runs this comparison after building the runtime. Full scoped global memory diagnostics still require typed load/store/atomic metadata, actual per-thread observed write versions, concurrent-grid ownership and synchronization lifecycle integration. Architectural capture continues to report fence ordering as a coverage gap until that model is implemented.
